## Part B1 — DecayPhase
Replaced the dual-scalar decay timer with the real 6-phase enum
(`HOLD_FRESH → BUILD → HOLD_FULL_SHROUD → EROSION → HOLD_FULL_SKELETON → ASH`),
each with its own config-driven duration (`PlayerCorpseConfig`) and a
resetting `phaseTicks` counter. **Flag: RECOVERY.md's own prose says the six
default durations sum to 12,000 ticks/10 minutes, but its own table's numbers
sum to 12,600/10.5 minutes** — implemented the table's explicit per-phase
values (2400/2400/1800/2400/1800/1800) since they're the more specific
source; this mismatch was never resolved, just implemented consistently one
way. `isDecayed()` kept (still called by `PlayerCorpseCorpseTracker`) but
redefined as `phase >= HOLD_FULL_SHROUD` — deliberately preserves the known,
accepted gap where the HUD arrow stops tracking well before a corpse could
ever reach the grave-marker moment. `EMPTY_DECAY_TICKS` now fast-forwards to
`HOLD_FULL_SKELETON` and lets the corpse decay+despawn naturally from there
(a deliberate behavior change from the old jar's "sits there decayed
forever" — judgment call, since an empty corpse has no loot to protect and
letting the world clean it up seemed better than the old dead-end state;
not explicitly specified either way in RECOVERY.md's new-system section).

## Part B2 — BlendedTextureCache + buildAlphaCurve
CPU-premixes two source stage textures into one real GPU texture
(`DynamicTexture`/`TextureManager`, verified against the real client jar via
`javap`), cached per (entity, slot), regenerated only when the blend
parameters actually change; `release()` called before every
re-registration so at most one live texture per (entity, slot) exists while
a corpse is alive (only the final generation outlives despawn - the
accepted tradeoff RECOVERY.md itself names). This is the fix for the
documented two-overlapping-transparent-draws flicker bug. Wired into the
EROSION phase's shroud crossfade. `buildAlphaCurve` (parabolic-eased ends,
linear middle, slope-matched at both 12% boundaries) replaces the BUILD
phase's old linear fade — verified numerically with a standalone harness
(f(0)=0, f(1)=1, monotonic, continuous slope at both boundaries), since this
can't be seen rendered in this environment.

## Part B3 — ash textures
`tools/generate_ash_texture.py` (Python 3.10 + Pillow/numpy, both installed
this session — neither existed on this machine beforehand) generates all 9
`ash_N.png` stages: an approximate extremity-weight map from the standard
64x64 player-skin UV layout (fingertips/rib-ends/skull-crown — **NOT
pixel-verified in-game**), smoothed noise widened in variance *and*
transition-softness for high-extremity regions (first attempt only widened
the noise itself and still fully saturated to a flat block by stage 4 -
caught by the same numerical verification approach, then fixed), local
histogram equalization before thresholding (fixes the historical
bell-shaped-distribution "nothing then everything" bug), colored
`DUST_HIGHLIGHT` not the rejected `EMBER_COLOR`. Verified numerically:
smooth monotonic mean-alpha progression stage 0→8, extremities reliably
ash before the torso core at every stage, per-pixel variance persists
through most of the sequence rather than clamping flat early. Composited
directly onto the skeleton texture as **the entity's base texture** during
ASH (not a separate RenderLayer at all) via `ashCollapseCurve` (first 82% of
raw duration → only 12% visible collapse, remaining 88% in the last 18%,
deliberately NOT smoothed at that breakpoint — an abrupt rate change is the
intended "stable then suddenly collapses" effect here).

## Part B4 — ash pose deformation
`ashPoseT(effective, hideAt)`: 0→1 smoothstep ramp over a 0.22 window
immediately before each part's own hide threshold, same effective-progress
timeline as the texture blend (no second clock). Thresholds
`ASH_HIDE_LIMBS_AT`(0.55)/`_HEAD_AT`(0.75)/`_BODY_AT`(0.95) are **my own
judgment call** — RECOVERY.md names the order and that body deforms last,
not exact numbers. Applied as small `+=` mutations after
`super.setupAnim()`'s frozen pose: limbs droop+splay (both axes fine, no
asymmetric texture), head tilts on `xRot` only (never `xRot`+`zRot` together
— composing both produces a corkscrew instead of a hinge-sag, visible on the
head's jaw-pivoted face texture), body sinks+caves last. Structural hiding
scales each part toward zero **before** flipping `ModelPart.visible`, never
the reverse. **Critical discipline applied throughout:** `resetAshState()`
unconditionally resets visibility/scale/body-y at the top of every
`setupAnim()` call, before any phase check — `this.head`/`body`/etc. are the
SAME shared `ModelPart` objects reused across every corpse rendered through
this one renderer instance (one instance per registered entity TYPE, not
per entity). Skipping this reset is exactly the cross-contamination bug
RECOVERY.md names as the priority historical issue; every mutated field here
is either unconditionally reset or freshly recomputed from that call's own
entity parameter, never read-modify-write against leftover state. Verified
numerically (thresholds fire in the documented order, ramps are correctly
bounded 0-1) — **the actual visual result (directions, whether it reads as
"giving way" vs. "wobbling") is completely unverified.**

## Part B5 — PlayerGraveMarkerEntity
Extends `LivingEntity` (like the corpse itself — no despawn checks, free
persistence). `transferFrom()` copies both containers then clears the
source (prevents double-dropping when the corpse discards right after).
Reuses `PlayerCorpseMenu`/its screen/networking completely unchanged —
confirmed by reading `PlayerCorpseMenu.java` first, it only ever takes plain
`Container` instances, never anything corpse-instance-specific. Registered
via `DeferredRegister` + its own `EntityAttributeCreationEvent` entry
(RECOVERY.md's explicit silent-NPE-at-construction trap for `LivingEntity`
subtypes). Wired into `PlayerCorpseEntity.completeAshAndDiscard()`: spawns
only if loot remains, then discards either way.
`GraveMarkerRenderer extends LivingEntityRenderer`, **not** `EntityRenderer`
— confirmed via the real API that only `LivingEntityRenderer#render` applies
the automatic `poseStack.scale(-1,-1,1)` this exact cross-shape model needs
to render right-side up. Simple two-box cross
(`MeshDefinition`/`PartDefinition`/`CubeListBuilder`, all verified via
`javap` against the real client jar before use — a registration path
[`RegisterLayerDefinitions`] not used anywhere else in this codebase),
textured with vanilla's own `textures/block/oak_planks.png`, no new assets.

## Part C — ASH-phase crash fix (BlendedTextureCache base-texture bounds)
**Fixed. Root cause confirmed from a real crash report, not guessed:**
`IllegalArgumentException: (0, 32) outside of image bounds (64, 32)` in
`NativeImage.getPixelRGBA`, via `BlendedTextureCache.blend` ←
`ashTextureFor`. `blend()` looped `x/y` over `stageLow`'s dimensions (the
ash stage textures, 64x64 player-skin format) and read `baseTexture` at the
same `(x, y)` unconditionally. `ashTextureFor` passes vanilla's own
`textures/entity/skeleton/skeleton.png` as `baseTexture` — confirmed via
`javap` against the real (mapped, NeoForge-patched) client jar that
`SkeletonModel.createBodyLayer()` declares `LayerDefinition.create(mesh, 64,
32)`, the legacy 64x32 mob-texture format, not 64x64. Once `y` reached 32,
`base.getPixelRGBA(x, 32)` threw. Shroud/erosion never crash because that
crossfade calls `getOrCreate(..., null)` — no `baseTexture` at all — so this
only ever manifested in ASH, the only phase that composites onto the
skeleton texture.

**Fix:** clamp the `baseTexture` read coordinates into its own real
`getWidth()`/`getHeight()` bounds (`Math.min(x, baseWidth-1)` /
`Math.min(y, baseHeight-1)`) instead of assuming it shares `stageLow`'s
dimensions. Considered and rejected padding/upscaling the skeleton texture
to 64x64 before blending: unnecessary work, since reading
`SkeletonModel.createBodyLayer()`'s decompiled source (via the real client
jar, not assumed) shows every one of its cube `texOffs` values falls within
`v=0-31` — the skeleton model's geometry never samples texture rows below
its own declared 32px height regardless of what's in that region of the
composited result, so clamping (which stretches the base's last real row
into the padding region) is visually inert for this specific case *and* a
general, non-skeleton-specific fallback for any future mismatched
`baseTexture`. Confirmed `NativeImage`'s real API via `javap` on
`compiledWithNeoForge_..._output.jar` in the NeoFormRuntime cache (the raw
client jar doesn't have Mojang-mapped names) —
`getWidth()`/`getHeight()`/`getPixelRGBA(int,int)`/`setPixelRGBA(int,int,int)`
all exist exactly as already used elsewhere in this file, no hardcoded
64x64 anywhere in `blend()`.

Verified: `compileJava` and `./gradlew build` both actually ran (this
environment had no JDK on `PATH`/`JAVA_HOME` at session start — found and
used the JDK 21 already present at
`B:\Claude\Projekte\_RECOVERY\tools\jdk-21.0.12+8` for both `javap` and the
Gradle build itself). Extracted `BlendedTextureCache.class` from the actual
built `build/libs/playercorpse-1.0.0.jar` (this project has no

`tools/verify_blend_bounds.py` (new) numerically re-implements

stage-pair + 64x32 base and confirms: correct 64x64 output shape, no
exception, full opacity everywhere, in-bounds rows match direct

row, and the `baseTexture=null` shroud-crossfade path is byte-for-byte
unaffected by the change.
